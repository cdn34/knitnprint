# Terraform in KnitNPrint: developer guide

## Mental model

```text
*.tf files -> Terraform CLI -> provider plugin -> AWS API
                 |
                 `-> state: resource address <-> real AWS resource ID
```

- Terraform CLI parses HCL, builds the dependency graph, calculates a plan,
  stores state, and asks providers to perform operations.
- The AWS provider is a separate executable plugin. It translates resources
  such as `aws_s3_bucket` into AWS API calls.
- Configuration is desired state. Terraform compares configuration, saved
  state, and the current AWS API response to produce a plan.
- State records which real object belongs to each Terraform address. Never edit
  it manually or commit it.

## Project layout

```text
infrastructure/terraform/
|-- staging/
|   `-- bootstrap/       # staging root module; runnable now
|-- production/          # separate future production roots
`-- README.md            # environment naming and isolation rules
```

A directory containing `.tf` files is a module. The directory passed through
`-chdir` is the root module for that command. Terraform combines every `.tf`
file directly inside that directory as if it were one document. File names are
for organization only: `state.tf` has no special behavior.

Nested directories are separate modules. Terraform does not automatically load
them. A root must explicitly call reusable code with a `module` block.

Do not combine staging and production with Terraform workspaces. They use
separate roots, backend buckets, state, credentials, names, and AWS resources.

## Current bootstrap files

Root: `infrastructure/terraform/staging/bootstrap`

| File | Purpose |
| --- | --- |
| `versions.tf` | Requires Terraform `~> 1.16.0` and AWS provider `~> 6.0`. |
| `providers.tf` | Configures the default AWS provider in `eu-west-1` and aliased `aws.identity` in `us-east-1`. Both use the administrator SSO profile for bootstrap. |
| `variables.tf` | Declares external inputs, their types, defaults, descriptions, and validation rules. |
| `terraform.tfvars.example` | Safe template for user-supplied values. Copy to ignored `terraform.tfvars`; do not put personal values or secrets in committed files. |
| `data.tf` | Reads account/Identity Center information and defines computed local values, names, and common tags. |
| `state.tf` | Creates and protects the dedicated staging state bucket. |
| `budget.tf` | Creates the staging monthly budget and email notifications. |
| `deployer.tf` | Defines the staging deployer policy, Identity Center permission set, and group assignment. |
| `outputs.tf` | Exposes values needed after apply, such as the generated state bucket name. |
| `backend.tf` | Configures the deployed staging state bucket after the one-time local bootstrap apply. |
| `.terraform.lock.hcl` | Pins the selected provider build and checksums. Commit this file. |
| `.terraform/` | Downloaded provider binaries and module cache. Generated by `init`; ignored by Git. |

## HCL blocks used here

### Terraform and provider requirements

```hcl
terraform {
  required_version = "~> 1.16.0"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}
```

`~> 1.16.0` permits Terraform `1.16.x`, but not `1.17.0`.
`~> 6.0` permits AWS provider `6.x`, but not `7.0`.

The constraint defines compatible versions. The lock file records the exact
selection, currently AWS provider `6.62.0`, plus package checksums.

### Provider configurations and aliases

```hcl
provider "aws" {
  profile = var.aws_profile
  region  = var.aws_region
}

provider "aws" {
  alias   = "identity"
  profile = var.aws_profile
  region  = var.identity_region
}
```

An AWS resource uses the unaliased provider by default. A resource or data
source that must use the Identity Center Region selects the alias explicitly:

```hcl
data "aws_ssoadmin_instances" "current" {
  provider = aws.identity
}
```

`profile` selects the AWS CLI SSO profile. The provider binary and repository do
not contain the credentials. `aws sso login` supplies a temporary session.

### Variables

```hcl
variable "monthly_budget_usd" {
  type    = number
  default = 120

  validation {
    condition     = var.monthly_budget_usd > 0
    error_message = "monthly_budget_usd must be greater than zero."
  }
}
```

Reference it as `var.monthly_budget_usd`. Values can come from the following
sources; later sources override earlier ones:

1. the variable's `default`;
2. a `TF_VAR_monthly_budget_usd` environment variable;
3. `terraform.tfvars`;
4. `*.auto.tfvars`, in lexical order;
5. `-var-file=...` and `-var=...`, in command-line order.

For this project, prefer an ignored `terraform.tfvars` for local bootstrap
values. Secrets will later come from an approved secret workflow, not committed
`.tfvars` files.

### Locals

```hcl
locals {
  environment       = "staging"
  name_prefix       = "knitnprint-${local.environment}"
  state_bucket_name = "${local.name_prefix}-terraform-state-${local.account_id}"
}
```

Locals name or transform values inside a module. Reference them as
`local.name_prefix`. Unlike variables, callers cannot override them.

### Data sources

```hcl
data "aws_caller_identity" "current" {}

locals {
  account_id = data.aws_caller_identity.current.account_id
}
```

A `data` block reads an existing object; it does not declare ownership of that
object. Here it reads the account ID from STS. Terraform may query data sources
during refresh or plan.

### Resources

```hcl
resource "aws_s3_bucket" "terraform_state" {
  bucket = local.state_bucket_name

  lifecycle {
    prevent_destroy = true
  }
}
```

The address is `aws_s3_bucket.terraform_state`:

- `aws_s3_bucket` is the provider resource type;
- `terraform_state` is our local name inside this module.

The local name is not automatically the AWS bucket name. The `bucket` argument
sets that real name.

Some AWS concepts use several Terraform resources. Our state bucket has
separate resources for the bucket, ownership controls, public-access block,
versioning, encryption, and bucket policy. This mirrors the AWS provider's
resource model and lets Terraform track each API object independently.

### References and dependencies

```hcl
resource "aws_s3_bucket_versioning" "terraform_state" {
  bucket = aws_s3_bucket.terraform_state.id
}
```

The reference creates an implicit dependency: create the bucket before enabling
versioning. Prefer references over `depends_on`. Use `depends_on` only when the
dependency exists but no value reference expresses it.

### Outputs

```hcl
output "state_bucket_name" {
  value = aws_s3_bucket.terraform_state.id
}
```

After apply:

```bash
terraform -chdir=infrastructure/terraform/staging/bootstrap output
terraform -chdir=infrastructure/terraform/staging/bootstrap output -raw state_bucket_name
```

## What the downloaded AWS provider is

`terraform init` read `versions.tf`, selected a compatible provider, verified
its checksum, and installed this executable locally:

```text
.terraform/providers/registry.terraform.io/hashicorp/aws/6.62.0/linux_amd64/
```

It is not part of Terraform CLI and is unrelated to the Rust AWS SDK used by the
backend. The two pieces of software call AWS independently:

```text
Terraform AWS provider -> creates/configures AWS infrastructure
Rust AWS SDK            -> application reads/writes S3 objects at runtime
```

Run these after changing a provider constraint or moving a Terraform root:

```bash
terraform -chdir=infrastructure/terraform/staging/bootstrap init -backend=false
terraform -chdir=infrastructure/terraform/staging/bootstrap providers
```

Use `terraform init -upgrade` only as an intentional dependency upgrade. Review
the resulting lock-file change and rerun validation and planning.

## Can we use more providers?

Yes. A root can use multiple provider types and multiple configurations of the
same provider.

We already use two configurations of `hashicorp/aws`: default Ireland and the
`aws.identity` alias in North Virginia. A future CloudFront certificate can use
another clearly named `us-east-1` alias.

To add another provider type:

```hcl
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
    example = {
      source  = "publisher/example"
      version = "~> 1.0"
    }
  }
}

provider "example" {
  # provider-specific authentication/configuration
}
```

Then run `terraform init`. Terraform downloads another plugin and adds it to the
lock file. Add a provider only when Terraform should own resources in that API.
Check its Registry publisher, maintenance tier, documentation, version history,
and authentication model first.

## How AWS resources are allocated in this project

Environment roots own environment state:

```text
staging root    -> knitnprint-staging-* resources -> staging state bucket
production root -> knitnprint-production-* resources -> production state bucket
```

Within a root, split files by concern for readability:

```text
network.tf       # VPC, subnets, routing, security groups
storage.tf       # media/admin/log buckets
database.tf      # RDS, subnet group, parameters
compute.tf       # ECS cluster, services, task definitions, ECR
edge.tf          # ALB, CloudFront, WAF, certificates
identity.tf      # workload roles and policies
observability.tf # log groups, alarms, notifications
```

All of those files still form one root and one dependency graph. When the two
environment roots need the same implementation, move the reusable resource
definitions into child modules:

```text
infrastructure/terraform/modules/storage/
infrastructure/terraform/modules/network/
infrastructure/terraform/modules/application/
```

Each environment calls the module independently and passes its own environment,
names, sizes, retention rules, and provider aliases. Modules share code, never
state or live resources.

Use this naming and tagging contract:

```text
Name:        knitnprint-<environment>-<purpose>[-<account-or-region>]
Application: knitnprint
Environment: staging | production
ManagedBy:   terraform
```

S3 names are globally unique, so append the account ID. Other resource names do
not need it unless AWS requires broader uniqueness.

## How to discover valid fields

Use these sources in this order.

### 1. Provider Registry documentation

Open the exact resource page and select provider version `6.62.0`. For example:

- `aws_s3_bucket`
- `aws_s3_bucket_versioning`
- `aws_ecs_service`
- `aws_db_instance`

The page lists arguments, nested blocks, exported attributes, import syntax,
timeouts, and behavior notes. Do not assume an old blog post matches provider
6.x.

### 2. The installed provider schema

List required/optional top-level S3 bucket fields from the exact installed
provider:

```bash
terraform -chdir=infrastructure/terraform/staging/bootstrap providers schema -json \
  | jq -r '
    .provider_schemas["registry.terraform.io/hashicorp/aws"]
    .resource_schemas["aws_s3_bucket"].block.attributes
    | to_entries[]
    | select(.value.required or .value.optional)
    | "\(.key): required=\(.value.required // false), optional=\(.value.optional // false), computed=\(.value.computed // false)"
  '
```

Inspect a nested block such as budget notifications:

```bash
terraform -chdir=infrastructure/terraform/staging/bootstrap providers schema -json \
  | jq '
    .provider_schemas["registry.terraform.io/hashicorp/aws"]
    .resource_schemas["aws_budgets_budget"].block.block_types.notification
  '
```

Schema flags mean:

- `required`: configuration must provide it;
- `optional`: configuration may provide it;
- `computed`: provider/AWS may determine it and expose it after refresh/apply;
- `optional + computed`: it can be configured, otherwise AWS/provider supplies
  a value.

### 3. Local validation and plan

```bash
terraform -chdir=infrastructure/terraform/staging/bootstrap fmt -check -recursive
terraform -chdir=infrastructure/terraform/staging/bootstrap validate
terraform -chdir=infrastructure/terraform/staging/bootstrap plan -out=staging-bootstrap.tfplan
terraform -chdir=infrastructure/terraform/staging/bootstrap show staging-bootstrap.tfplan
```

`validate` catches type/schema/reference errors without changing AWS. `plan`
also refreshes data from AWS and shows proposed changes. A successful plan is
not permission to apply it; review names, account, Region, replacements,
deletions, IAM scope, and cost first.

For IAM policies, a staging-looking resource name does not make a wildcard safe.
For example, `ec2:*` or `secretsmanager:*` with `Resource = "*"` and only a
Region condition could modify production resources in the same account and
Region. Start with exact Terraform-state permissions, then add service access
alongside each implemented stack when resource ARNs, name prefixes, and tags can
be constrained. Establish a permissions boundary before granting a deployer
permission to create or pass workload roles.

## Bootstrap workflow for this repository

Commands marked **AWS mutation** are the commands the project owner runs.

### 1. Create ignored local values

```bash
cp infrastructure/terraform/staging/bootstrap/terraform.tfvars.example \
  infrastructure/terraform/staging/bootstrap/terraform.tfvars
```

Set `budget_notification_email` in the copied file.

### 2. Authenticate and confirm the account

```bash
aws sso login --profile knitnprint-administrator
aws sts get-caller-identity \
  --profile knitnprint-administrator \
  --region eu-west-1 \
  --no-cli-pager
```

### 3. Initialize, format, and validate locally

```bash
terraform -chdir=infrastructure/terraform/staging/bootstrap init -backend=false
terraform -chdir=infrastructure/terraform/staging/bootstrap fmt -check -recursive
terraform -chdir=infrastructure/terraform/staging/bootstrap validate
```

### 4. Create and inspect a saved plan

```bash
terraform -chdir=infrastructure/terraform/staging/bootstrap plan \
  -out=staging-bootstrap.tfplan
terraform -chdir=infrastructure/terraform/staging/bootstrap show \
  staging-bootstrap.tfplan
```

Plan is read-only against AWS but writes an ignored local plan file.

### 5. Apply the exact reviewed plan — AWS mutation

```bash
terraform -chdir=infrastructure/terraform/staging/bootstrap apply \
  staging-bootstrap.tfplan
```

Using the saved plan ensures apply executes the reviewed proposal rather than
calculating a new one.

### 6. Read outputs

```bash
terraform -chdir=infrastructure/terraform/staging/bootstrap output
```

### 7. Migrate bootstrap state to S3 — state mutation

After the bucket exists:

1. Confirm `backend.tf` names the output bucket
   `knitnprint-staging-terraform-state-739863594156`.
2. Confirm the key is `staging/bootstrap/terraform.tfstate`.
3. Run:

```bash
terraform -chdir=infrastructure/terraform/staging/bootstrap init -migrate-state
```

Read the migration prompt carefully before approving the state copy. Then run a
new plan; it should report no infrastructure changes.

## Everyday change workflow

```bash
# Edit .tf files
terraform -chdir=<environment-root> fmt -recursive
terraform -chdir=<environment-root> validate
terraform -chdir=<environment-root> plan -out=<reviewed-name>.tfplan
terraform -chdir=<environment-root> show <reviewed-name>.tfplan
# Owner runs only after review:
terraform -chdir=<environment-root> apply <reviewed-name>.tfplan
```

Key rules:

- Check the AWS account and Region before every apply.
- Commit `.tf` and `.terraform.lock.hcl`; never commit `.terraform/`, state,
  plans, or real `.tfvars`.
- Do not run `apply -auto-approve` for staging or production.
- Do not run `terraform destroy` as a routine stop command.
- If Terraform proposes replacing or deleting a state bucket, database,
  certificate, or identity resource, stop and investigate.
- If an AWS object exists outside Terraform, decide explicitly whether to leave
  it external, import it, or replace it. Do not declare it and hope Terraform
  adopts it automatically.
